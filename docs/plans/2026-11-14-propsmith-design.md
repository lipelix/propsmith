# propsmith: design

Date: 2026-11-14. Status: approved by the owner (cut, phases, hosting, plan tracking).

## Goal

A coding agent turns a sentence into a game prop: a Blender `bpy` script, built headless, measured, checked and looked
at until it passes. Finished props go into an open catalogue anyone can search and pull from. The first consumer is
[srd-iso-rpg](https://github.com/lipelix/srd-iso-rpg), whose own prop tooling this project is cut out of.

References: [text-to-cad](https://github.com/earthtojake/text-to-cad) (models as code, a skill for agents, snapshots for
arrangement and measurements for numbers, three-state checks) and
[step.parts](https://github.com/earthtojake/step.parts) (one catalogue, stable ids, strict metadata, PR-only
contributions, a search site and a JSON index).

## Decisions

| #   | Decision                                                                                                 | Why                                                                                                        |
| --- | -------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| 1   | The generator and the catalogue are cut out of srd-iso-rpg; srd consumes the catalogue.                  | One source of truth, usable by other games.                                                                |
| 2   | The canonical asset is the source (`asset.py` + `asset.json`); the GLB is derived from it.               | Source is small, reviewable text and rebuilds byte-identical. No Git LFS.                                  |
| 3   | Models are Blender `bpy` scripts on a small shape and material library, not CAD.                         | Game props need textures, wear and organic shapes; the library and checks already exist in srd.            |
| 4   | Public repo `lipelix/propsmith`, code MIT, catalogue assets CC0-1.0, textures only from a CC0 ledger.    | Anyone may use a prop in any game without asking.                                                          |
| 5   | The site is static, hosted on Cloudflare Pages with Cloudflare Web Analytics, set up as code (OpenTofu). | The owner wants Cloudflare's metrics; no server to run.                                                    |
| 6   | Game facts stay in the game.                                                                             | Tiles, cover, hit points, camera and post-processing differ per game; the catalogue stays engine-agnostic. |
| 7   | Work is tracked as an HQ plan: one plan issue, one sub-issue per task, one PR per task.                  | Same flow as the owner's other projects.                                                                   |

## The cut

Moves to propsmith (general):

- the `bpy` library: shapes, materials, registry (`@prop` variants, anchors), measure, export;
- `build` (headless Blender, input-hash cache), `check`, `new` (the `claude -p` loop), the texture ledger;
- the asset schema: search fields, size in metres, variants, anchors, provenance;
- checks: `bounds-fit`, `origin-ground`, `tri-budget`, `manifold`, `materials-known`, `anchors-declared`;
- the agent skill, the catalogue index and the site.

Stays in srd-iso-rpg (game layer):

- `prop.json` shrinks to an overlay: footprint in tiles, rotations, gameplay facts, bake mode, and the catalogue asset
  it uses;
- `style.json`, sprite rendering in the game camera, sheet packing, the location bake.

## Layout

```
lib/propsmith/        bpy library (Python, imported inside Blender)
tools/                TypeScript CLI: new, build, check, catalog, textures, publish
catalog/
  <id>/asset.py       the model
  <id>/asset.json     the facts code reads
  tags.json           tag vocabulary (facets)
  textures.json       CC0 texture ledger (url, sha256, licence)
  measurements.json   generated by build; what check reads without Blender
  index.json          generated; the public index
skills/prop/SKILL.md  the model contract and the loop, for agents
site/                 static catalogue (Vite + Preact), GLB viewer
infra/                OpenTofu: Pages project, DNS, Web Analytics
docs/plans/           design and plan
```

## Asset contract

`asset.json` (strict, unknown fields fail):

- `schema`, `id` (snake_case, stable), `name`, `description`
- `category`, `family`, `tags` (only from `tags.json`), `aliases`
- `variants`: ids in `asset.py` order, `<id>` or `<id>_<suffix>`
- `size`: `{ x, y, z }` in metres, the box the model must stay inside
- `anchors`: named points for effects (`light:`, `fire:`, `smoke:`, `water:`)
- `closed`: true when every part must be a closed mesh (for fracture or printing)
- `provenance`: `generated` (prompt) | `handwritten` | `pack`; `licence`

`asset.py`: metres, z up, origin at the centre of the base on the ground, front on -y, overall dimensions as named
constants, randomness only from fixed seeds, no file or network access, materials only from the library.

Generated per asset at publish: `<id>/<variant>.glb` (baked textures), `<id>/<variant>.png` (thumbnail), plus byte size
and SHA-256 in `index.json`.

## The loop

`npm run new -- <id> "<description>"` scaffolds a draft and runs `claude -p` with the skill, confined to the asset's
folder and to `npm run build -- <id>`. One round: write, build, read the check report (numbers come from here, never
from pictures), look at the snapshots (iso, top, front), fix. At most 5 rounds. A check is `OK`, `FAILED` or
`NOT CHECKED`; only all-`OK` may be published.

## GLB

The library's materials are procedural shader nodes, which glTF cannot carry. The publish step bakes base colour and
normal per variant (Cycles bake onto a generated UV atlas) and exports a GLB with plain PBR materials. This is the
main technical risk; the task has a stop-and-show gate comparing the GLB in a browser with the Blender render.

Games that render in Blender (srd) build from the source and the library instead, so their look does not depend on the
bake.

## How a game consumes it

- Discovery: the site, or `index.json` (id, name, tags, size, variants, asset URLs, hashes).
- Engines: download the GLB.
- Blender pipelines: pin the repo at a tag (`"propsmith": "github:lipelix/propsmith#vX.Y.Z"`), read
  `catalog/<id>/asset.py` and import `lib/propsmith`.

srd-iso-rpg does the last one: its `props:build` loads the catalogue asset, renders sprites with its own `style.json`,
and its input hash covers the pinned asset and library.

## Contributing

PR only. `npm run check` (schema, tags, measurements fresh, budgets; no Blender needed) runs in CI on every PR; a merge
to `main` builds the changed assets, bakes GLBs and publishes the site.

## Out of scope for now

Characters and animation, rigging, LODs, an upload form on the site, accounts, non-CC0 assets.
